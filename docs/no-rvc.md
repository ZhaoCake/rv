# no-rvc：删掉 C 扩展的魔改记录

| 项目 | 内容 |
|---|---|
| 分支 | `no-rvc`（基线 `main`） |
| 日期 | 2026-09-28 |
| 目标 | 通过"删功能"理解 C 扩展在 `rv.c` 里的完整影响面 |
| 结果 | `rv.c` **761 行 → 598 行**（净减 163 行）；`git diff main` = `+22 / -185` |
| 状态 | 编译零警告（`-Wall -Wextra -pedantic -Wshadow`），`example` 行为不变 |
| 未提交 | 改动都在工作区，未 commit |

---

## 1. 动机：为什么要做"减法"

读代码只能看到"这个功能怎么实现的"；删代码才能看到"这个功能牵扯了多少东西"。

三个预期收获：

1. 摸清 C 扩展在 `rv.c` 里的**完整影响面**，特别是那些"看不出跟 C 有关"的位置；
2. 验证一个判断：`rv_if` 里"拆成两次 2 字节取指"的分支，**首先是为对齐服务的，不是为跨页**；
3. 做一次真实的对齐语义实验：**缺少对齐检查时会发生什么**。

---

## 2. 魔改前的侦察：C 扩展的耦合清单

| # | 位置 | 内容 | 与 C 的关系 |
|---|---|---|---|
| 1 | `rv_init` 的 misa | `rv_ext('C')` 位 | 声明支持 |
| 2 | `rv_isz` 宏 | `(i & 3) == 3 ? 4 : 2` | 为"指令可能是 16 位"而生 |
| 3 | `rvc_*` 字段宏（14 个） | 压缩格式的位段提取 | 只在解压时用 |
| 4 | `rv_i_*` 组装宏（6 个） | 把 C 指令拼成 32 位等价值 | **注释自称通用，实则只为解压服务** |
| 5 | `rvc()` 函数 | 压缩指令解压表，87 行 | 全部 |
| 6 | `rv_if` 的拆分分支 | `cpu->pc & 2 \|\| page` | **因为 pc 只保证 2 字节对齐**——最大的隐形影响 |
| 7 | `rv_if` 的解压调用 | `*i = rvc(*i & 0xFFFF)` | 全部 |
| 8 | `rv_step` 的长度检查 | `rv_isz(i) != 4 → RV_EILL` | 解压后恒不成立，形同摆设；去 C 后**才真正生效** |
| 9 | `jalr` | `target & ~1U` | 2 字节对齐是有 C 时的合法目标 |

合计约 130 行，占全部代码的 **17%**。其中第 4、6 项最容易被误认为与 C 无关。

## 3. 五刀记录

### 第 1 刀：摘除解压能力（761 → 671）

| 改动 | 内容 |
|---|---|
| a | `rv_init` 的 `misa` 删除 `\| rv_ext('C')` |
| b | `rv_if` 删除 `if (rv_isz(*i) < 4) *i = rvc(*i & 0xFFFF);` |
| c | 删除 `rvc()` 函数（89 行） |

**关键点**：没有新增任何"拒绝压缩指令"的代码。原来 `rv_step` 里早就有一道长度检查 `if (rv_isz(i) != 4) return rv_trap(cpu, RV_EILL, tval);`，它在有解压时永远不成立；撤掉解压后，这道防线**自动复活**——16 位指令直接撞上它。

> 教训：补丁会掩盖下层已有的检查。删掉补丁，防线自己就显现了。

**验证**：`example.c` 仍输出 `Environment call @ 80000004: 42`；压缩指令 `0x0505` 返回 `RV_EILL(2)`。

### 第 2 刀：清理孤儿宏（671 → 626）

删除 44 行：

- `rvc_*` 系列 14 个：`rvc_op`、`rvc_f3`、`rvc_rp`、`rvc_ird`、`rvc_irpl`、`rvc_irph`、`rvc_imm_ciw/cl/ci/ci_b/ci_c/cj/cb/css`
- `rv_i_*` 系列 6 个：`rv_i_i`、`rv_i_s`、`rv_i_u`、`rv_i_r`、`rv_i_j`、`rv_i_b`

**注意**：`rv_i_*` 那组的注释写的是"组装所有非压缩指令类型的宏"，语气像通用基础设施，其实**只被解压表用过**。宏不会被编译器警告未使用，所以它们会安静地留下来骗读者。

**保留** `rv_isz`——它还剩两处用途（`rv_if` 算 `next_pc`、`rv_step` 作长度防线）。

> 教训：别信注释里的自我定位，看谁在调用它。

### 第 3 刀：补 `pc` 对齐检查（626 → 633）

```c
rv_u32 rv_step(rv *cpu) {
  rv_u32 i, tval, err;
  if (!++cpu->csr.cycle)
    cpu->csr.cycleh++; /* 带进位地累加到 cycle、cycleh */
  /* no-rvc 分支新增：没有 C 扩展时指令必然 32 位，pc 必须四字节对齐。 */
  if (cpu->pc & 3)
    return rv_trap(cpu, RV_EIALIGN, cpu->pc);
  err = rv_if(cpu, &i, &tval); /* 取指令到 i */
  ...
```

三点说明：

1. **顺序**：cycle 递增 → 对齐检查 → 取指。必须在取指**之前**检查，否则一个越界的非法地址会先报 `RV_EIFAULT` 而不是 `RV_EIALIGN`。
2. **`tval`**：传 `cpu->pc`，因为对 `instruction-address-misaligned` 而言，`mtval` 记录的是**出错地址**（而非指令编码）。
3. **`jalr` 故意不改**：RISC-V 规范要求 JALR 只把目标地址的 **bit 0** 清零，剩下的对齐由取指阶段检查。若在 `jalr` 里写成 `target & ~3U`，就成了"静默修正非法地址"，异常永远报不出来。

> 教训：该报错的地方要报错，不要顺手替调用者擦屁股。

### 第 4 刀：简化取指路径（633 → 627）

`pc` 已被强制四字节对齐后，`rv_if` 里的 `page` 变量和整个"拆成两次 2 字节取指"分支都成了死代码：

```c
static rv_u32 rv_if(rv *cpu, rv_u32 *i, rv_u32 *tval) {
  rv_u32 err, pc = cpu->pc;
  if ((err = rv_bus(cpu, &pc, (rv_u8 *)i, 4, RV_AX))) /* 4 字节取指 */
    goto error;
  cpu->next_pc = cpu->pc + rv_isz(*i);
  *tval = *i; /* 对非法指令 trap 而言，tval 是原始指令 */
  return RV_OK;
error:
  *tval = pc; /* 对指令 {page}fault trap 而言，tval 是 pc */
  return err;
}
```

### 第 5 刀：删除 `rv_bus` 的跨页分支（627 → 598）

删除 29 行，包括那段"跨页拆分"的代码和它上面冗长的缺陷分析注释，并同步更新函数头职责（去掉"跨页拆分"）与 `va` 参数语义（`[进/出]` → `[进]`）。

**为什么可以删**——三条路径全部被堵死：

| 路径 | 保证 |
|---|---|
| 数据访问 | 地址按 `width` 对齐，且 `4096 % width == 0` |
| 取指 | `pc` 强制四字节对齐（第 3 刀）+ 固定 4 字节取指（第 4 刀） |
| 页表访问 | 内部构造的地址 4 字节对齐、宽度 4 |

**为什么应该删**——错误的死代码比没有代码更危险：

1. 它不可达 ⇒ 永远不会被测到 ⇒ 三个缺陷（`ledata` 偏移 ×2、`rv_vmm` 硬编码 `RV_AW`）可以潜伏到天荒地老；
2. 一旦有人放开对齐检查（比如加非对齐访存支持），它会**瞬间复活**，带着 bug 一起；
3. 它会**骗读者**：看到 `if (跨越页边界)` 会以为跨页已被妥善处理，从而不再追问"到底还会不会跨页"——而这个追问本身才是理解 `rv` 的关键。

> **将来若要恢复跨页处理，不要 `git revert` 这段代码**——它本身是错的。正确做法：两段分别写进 `ledata` 的不同偏移，收尾用**原始的** `data` 与 `width` 一次性搬回。

## 4. 关键发现（值得记住的六条）

1. **C 扩展在 `rv` 里的唯一"特权"就是那个解压动作**。撤掉它，剩下的下游代码全都按"指令必须是 32 位"写好了。
2. **`rv_if` 的拆分分支首先是为对齐**：`pc = 0x...002` 处可以合法地放一条 32 位指令（C 扩展只要求 2 字节对齐），但 4 字节取指要求 4 字节对齐，所以必须拆。跨页只是这个条件的副产品（`0xFFE` 恰好同时满足两者，`0x002` 只满足前者）。
3. **`rv_bus` 的跨页分支不可达的证明**：对齐检查保证 `pa` 的页内偏移是 `width` 的倍数，而 `4096` 也是 `width`（1/2/4）的倍数，所以 `off` 最大只能到 `0x1000 - width`，`off + width - 1 ≤ 0xFFF`，永不越页。
4. **`mtval` 的语义随异常类型变化**：非法指令存**指令编码**，缺页/访问异常存**出错地址**。`rv_if` 里 `*tval = *i` 与 `error: *tval = pc` 两行就是为此分设的。
5. **缺少对齐检查的后果不是"报错"，而是"把非法地址解释成一串合法指令"**（见第 5 节的对比实验）。
6. **接口的诚实性**：`va` 之所以是 `rv_u32 *va`，唯一理由就是跨页时要就地前移；跨页处理删掉后，这个指针参数已经名不副实。

## 5. 复现验证

### 编译与基础回归

```powershell
gcc --std=c89 -Wall -Wextra -pedantic -Wshadow -g -I. rv.c tools/example/example.c -o example.exe
./example.exe
# 期望：Environment call @ 80000004: 42
```

### 探针 A：压缩指令应被拒绝

程序第一条是 `c.addi a0, 1`（编码 `0x0505`，低 2 位 `01` ⇒ 16 位指令）：

```c
rv_u32 program[2] = {
    0x00000505, /* c.addi a0, 1 */
    0x00000073, /* ecall */
};
```

| 分支 | `rv_step` 返回 | `mtval` | 说明 |
|---|---|---|---|
| `main` | `0x80000010`（RV_TRAP_NONE） | `0` | 解压成 `addi a0, a0, 1` 后正常执行 |
| `no-rvc` | `2`（RV_EILL） | `0x00000505` | 撞上长度检查；`mtval` 是指令编码 |

### 探针 B：`jalr` 跳到非四字节对齐地址

```c
rv_u32 program[4] = {
    0x800000B7, /* lui  x1, 0x80000   x1 = 0x80000000 */
    0x00608093, /* addi x1, x1, 6     x1 = 0x80000006（只 2 字节对齐） */
    0x00008067, /* jalr x0, 0(x1)     跳过去 */
    0x00000073, /* ecall */
};
```

`no-rvc` 的结果：

```
step 1: ret = 80000010          （RV_TRAP_NONE）
step 2: ret = 80000010
step 3: ret = 80000010
step 4: ret = 00000000          （RV_EIALIGN，cause = 0）
        mcause = 0   mtval = 80000006
```

`main` 的结果：**6 步全是 `80000010`，永不报错**。原因是：

```
pc = 0x80000006（2 字节对齐）
  ├─ rv_if 走拆分路径，取 2 字节得到 0x0060
  ├─ rvc(0x0060) 解压出 addi x8, x2, 12      ← 一条"看起来合法"的指令
  ├─ 但 next_pc = pc + rv_isz(*i)，而 *i 是【解压前】算的 ⇒ +2 ⇒ 0x80000008
  └─ pc = 0x80000008 取到那条 jalr ⇒ 又跳回 0x80000006 ⇒ 死循环
```

**这就是"没有对齐检查"的真实后果**：非法地址不会被拒绝，而是被强行解释成合法指令流，最后陷入荒诞的循环。

## 6. 影响与限制

- **现成的 Linux 镜像跑不了**（注意：这不等于"Linux 跑不了"）。本仓库默认构建出的镜像按 `rv32imac` 编译，里面全是 C 指令，直接用本分支运行会在用户空间崩掉。相关配置在 `tools/linux/extern/configs/rv_defconfig`：`BR2_RISCV_ISA_RVC=y`、`PLATFORM_RISCV_ISA=rv32imaczicsr_zifencei`。
- **但 C 扩展并不是 Linux 的必要条件**：内核（`CONFIG_RISCV_ISA_C`）、OpenSBI（`PLATFORM_RISCV_ISA`）、buildroot（`BR2_RISCV_ISA_RVC`）三处开关全都可以关。真正的障碍在工具链的 multilib——详见 [`no-rvc-toolchain.md`](no-rvc-toolchain.md)。
- **riscv-tests**：`rv32ui/rv32mi/rv32si/rv32um/rv32ua`（无 C 版本）理论上应全过，`rv32uc`（压缩指令）应全挂。跑之前记得删掉 `tools/test/Makefile` 里这一行，否则 C 测试向量会被拉进来集体失败：

  ```make
  cp $(RISCV_TESTS)/isa/rv32uc-p-* vectors
  ```

- 本分支保留了对齐检查，因此**不支持非对齐数据访存**（抛 `RV_ELALIGN`/`RV_ESALIGN`），这与 `main` 一致，是 RISC-V 允许的实现选择。

## 7. 后续可做

1. **简化 `rv_bus` 签名**：`rv_u32 *va` → `rv_u32 va`（值传递）。收益是接口诚实，成本是同步改 5 个调用点（`rv_if` 1 处、`rv_step` 的 LOAD/STORE/AMO 共 4 处）。注意 `rv_step` 内部的 `va` 局部变量仍需保留（trap 时要报地址）。
2. **`rv_isz` 的去留**：现在只剩两处用途。可以删掉它（`next_pc` 恒为 `pc + 4`，长度检查直接写 `(i & 3) != 3`），也可以留着保留"指令长度"语义。这是自由度，不是对错。
3. **跑一次 riscv-tests**：检验这次改动是否真的只影响 C 扩展。
4. **对照实验**：把第 3 刀的对齐检查临时注释掉，观察探针 B 是否退化成 `main` 的死循环行为——亲手确认"检查缺失"的后果。
