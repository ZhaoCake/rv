# 扩展取舍与微架构取向

> 记录两类内容：
> ① **ISA 扩展的必要性分层**（哪些是跑 Linux 的硬需求，哪些可以砍）；
> ② **未来 CPU 实现的路线倾向**（单发 vs 超标量、乘法器/除法器的取舍）。
>
> 相关文档：[`no-rvc.md`](no-rvc.md)（从模拟器侧移除 C 扩展）、[`no-rvc-toolchain.md`](no-rvc-toolchain.md)（无 C 软件栈的构建约束）

---

## 一、ISA 扩展必要性总表

| 扩展 / 特性 | 跑 Linux 的必要性 | 说明 |
|---|---|---|
| RV32I / RV64I 基础 | **必需** | 指令集根本 |
| Zicsr | **必需** | `mstatus` / `satp` / `mepc` / `mcause` / `stvec` 全靠它 |
| Zifencei（`fence.i`） | **必需** | 指令缓存同步；模块加载、`flush_icache` 依赖它 |
| A（原子） | **必需** | 自旋锁、原子计数器；缺了内核无法工作 |
| S 模式 | **必需** | Linux 内核跑在 S 模式，M 模式归固件 |
| Sv32 / Sv39 MMU | **必需** | 虚拟内存是内核地基 |
| M（乘除） | **规范上可选** | 可以用软件库替代（见第二节），代价是性能与复杂度转移 |
| C（压缩） | **可选** | 纯代码体积 / 取指效率优化，代价是前端复杂度（见 `no-rvc.md`） |

**一句话**：必需的那几项构成"能跑"的底线；M 和 C 都是"用面积/复杂度换性能"的选项，只是换的地方不同——C 换的是**前端**，M 换的是**算术单元**。

## 二、M 扩展砍掉之后：软件算术的分层

这里有个常见误解要澄清：**内核里的软件除法（`div64.c`）并不是"无 M"的补偿**，它解决的是另一个问题。

### 2.1 先分清 32 位与 64 位

| 运算 | 谁提供 | 无 M 时 |
|---|---|---|
| **32 位** `mul`/`div`/`rem` | **M 扩展硬件指令** | 编译器生成 `__mulsi3` / `__divsi3` / `__udivsi3` / `__modsi3` / `__umodsi3` 调用，由软件库实现 |
| **64 位**（RV32 上的 `long long`） | **本来就没有指令** | **永远**靠软件模拟，与 M 无关 |

所以"RV32 上的 64 位算术必须有人补"是一条恒定事实，区别只在于补在**指令集里**还是补在**库里**。

### 2.2 用户态：libgcc，编译器自动处理

```
-march=rv32ima   →  a * b 编成 mul 指令
-march=rv32i     →  a * b 编成 call __mulsi3
```

- 通用实现：`gcc/libgcc/libgcc2.c`（`__mulsi3`、`__udivmodsi4` 等）
- RISC-V 特有优化（若有）：`libgcc/config/riscv/`
- 链接由 GCC 自动带上，**应用层面完全透明**

### 2.3 内核态：不能靠 libgcc，得自己提供

- 内核**不链接 libgcc**，所以无 M 时那些 `__mulsi3` 符号要内核自己补（放进 `arch/riscv/lib/`）。
- 更关键的是：**RISC-V 内核把 `m` 写进了基础 march 串**，没有 Kconfig 开关：

  ```make
  # arch/riscv/Makefile（大致形式）
  riscv-march-$(CONFIG_ARCH_RV32I)  := rv32ima          # ← m、a 固化
  riscv-march-$(CONFIG_RISCV_ISA_C) := $(riscv-march-y)_c   # ← 只有 c 可选
  ```

- 核实方法（在内核源码里）：

  ```shell
  git grep -n "riscv-march" arch/riscv/Makefile
  git grep -n "RISCV_ISA_M" arch/riscv/Kconfig
  ```

  若搜不到 `ISA_M`，即证明"无 M"不是官方支持的配置。

**结论**：无 C 是官方支持的配置项；无 M 需要改 Makefile + 补 libgcc 例程，属于非常规路径。

### 2.4 内核里真正的软件算术（与 M 无关）

| 文件 | 内容 |
|---|---|
| `lib/div64.c` | `div64_u64` / `div64_s64`——用 32 位指令做 64 位除法 |
| `include/asm-generic/div64.h` | `do_div()` 宏，内核最常用的 64 位除法接口 |
| `lib/muldi3.c` | `__muldi3`（64×64 → 低 64 位） |

注意：`arch/riscv/lib/` 里**没有** `__mulsi3` ——因为内核假定 M 存在。这反过来印证了上面的判断。

### 2.5 若真要做无 M 内核，需要补的清单

1. 改 `arch/riscv/Makefile` 的 march 串（去掉 `m`）
2. 提供 `__mulsi3` / `__divsi3` / `__udivsi3` / `__modsi3` / `__umodsi3`（可从 libgcc 抽取）
3. 视编译器生成情况补 `__muldi3` 等 64 位助手
4. 排查内核中假设 M 存在的内联汇编

### 2.6 两个旁证：硬件设计者也在做同样的取舍

- **`-mno-div`**：即使有 M，GCC 也可以强制使用软件除法——说明"硬件除 vs 软件除"在工具链层面是可选项。
- **`Zmmul` 扩展**：**只有乘法、没有除法**。它存在的理由就是**除法器的面积远大于乘法器**（多周期迭代或更大的组合逻辑）。这是"半 M 扩展"，与"不要 C"属于同一类决策。

## 三、微架构取向（路线倾向）

> 以下为当前的设计倾向，属于待定决策，随时可被实测数据推翻。

### 3.1 若目标是"先把 Linux 跑起来"，倾向单发顺序流水线

| 决策 | 倾向 | 理由 |
|---|---|---|
| 流水线 | **单发（single-issue）顺序** | 复杂度与验证成本最低；Linux 的正确性不依赖吞吐 |
| 除法器 | **不做**，用软件除法 | 除法器面积/时序代价大，是"最贵的一块算术"；软件除法在功能上等价 |
| 乘法器 | **视情况**（面积/时序允许就做） | 乘法比除法便宜得多，且内核里乘法调用频率高于除法 |

自洽性检查：Linux 只需要**功能正确**，不要求**指令吞吐**。用 libgcc / `div64.c` 的软件乘除，功能上完全等价，代价只是性能——而"先跑起来"阶段性能不是首要指标。

### 3.2 若要上超标量，则乘除法器必须先有

理由：

- 超标量的价值在于"每周期多发"，而软件乘除会**占满发射槽并阻塞**，把多发射的优势吃掉；
- 软件乘除需要额外的调用/返回和寄存器压力，在乱序或双发场景下代价被放大；
- 追求超标量本身就意味着目标场景对性能敏感，此时面积的边际成本可以接受。

**结论**：`除法器` 的有无，实际上是"单发 vs 超标量"这个更大决策的**下游结果**，而不是独立选项。

### 3.3 Zbb / Zmmul / M 的作用域（正交，不可互相替代）

> 修正一个容易搞混的判断：**Zbb 与 Zmmul 不是替代关系**，它们解决的是不同问题。

| 配置 | 硬件提供 | 能消掉的软件例程 | 仍然需要软件实现的 |
|---|---|---|---|
| 无 M | — | 无 | `__mulsi3` + `__divsi3` / `__udivsi3` / `__modsi3` / `__umodsi3` |
| **Zmmul** | `mul` / `mulh` / `mulhu` / `mulhsu` | **`__mulsi3`**（以及部分 64 位乘法助手） | 除法四件套 |
| **Zbb** | 位操作（`clz`/`ctz`/`cpop`/`rol`/`ror`/`rev8`/`min`/`max`/`sext.*`…） | **一个都消不掉** | 乘法和除法全部保留 |
| Zmmul + Zbb | 乘法 + 位操作 | `__mulsi3` | 除法四件套（但循环跑得更快） |
| M | 乘 + 除 | 全部 | — |

**三条要点：**

1. **Zbb 对乘法没有帮助**。它没有任何乘法指令；软件乘法 `__mulsi3` 的经典实现是移位-加法，循环次数由操作数位数自然决定（`while (b) { ... b >>= 1; }`），与 `clz` 无关。所以"只有 Zbb 没有 Zmmul"时，`a * b` 依然慢。
2. **Zbb 的作用是"加速"，不是"替代"**。它把软件除法的迭代次数从"固定 32/64 次"降到"有效位数差"（迭代次数 ≈ `fls(dividend) - fls(divisor) + 1`，而 `fls` 正是 `clz` 的用途），但软件除法本身还在。
3. **常数除法优化（`x / 7` → 魔数乘法 + 移位）依赖的是 Zmmul，不是 Zbb**——它需要 `mul` + `mulhu` 取乘法高半，Zbb 做不到。

### 3.4 实施阶段划分与扩展优先级

#### 阶段 0：功能跑通（唯一目标，不追性能）

**目标 ISA：`rv32ia_zicsr_zifencei`**（外加核级的 S 模式与 Sv32 MMU）。

- 这是"能跑 Linux"的**最小集**：A / Zicsr / Zifencei 缺一不可，缺了内核起不来。
- **本阶段不引入任何性能扩展**（Zbb、Zmmul、除法器全部往后放）。
- 需要自己动手的四处（都是非官方路径，因为内核把 `m` 写死了）：
  1. 改内核 `arch/riscv/Makefile` 的基础 march 串，去掉 `m`
  2. 提供 `__mulsi3` / `__divsi3` / `__udivsi3` / `__modsi3` / `__umodsi3`（内核不链 libgcc）
  3. OpenSBI 的 `PLATFORM_RISCV_ISA` 同步改
  4. 工具链 multilib 要匹配（见 [`no-rvc-toolchain.md`](no-rvc-toolchain.md)）
- **模拟器侧已就绪**：`no-rvc` 分支的 `rv.c` 实现了 I / A / M / Zicsr / Zifencei / S 模式 / Sv32，功能上已覆盖本阶段要求。多出的 `M` 无害——软件按 `rv32ia` 编译时不会生成 `mul`/`div`（这是编译期决定的）。

> **降风险做法（建议）**：分两小步走。
> `0a` 先用官方支持的 `rv32ima_zicsr_zifencei` 把整条链路跑通（排除工具链、内核配置、设备树、SBI 等非 ISA 变量）；
> `0b` 再单独切到无 `m` 的配置。**一次只改一个变量**，否则失败时分不清是"无 M 的坑"还是别的配置问题。
> 总之大概就是，先用qemu或者这个模拟器跑动了软件层面确认可用，再考虑转到硬件上（之后的学习中，我将会了解特权架构的实现以及测试方法）

#### 阶段 1+：按实测瓶颈逐个加

| 顺序 | 扩展 | 依据 |
|---|---|---|
| 1 | **Zbb** | 面积最小（大量指令是连线级、复用现有 ALU）；内核 `fls()` 会自动升级为 `clz`；顺带加速软件除法 |
| 2 | Zmmul | 消除 `__mulsi3`；让"除以常数"被编译器优化成乘法 |
| 3 | 除法器 | 最贵；等确认有必要（例如要上超标量，或实测发现运行时除法是瓶颈） |

**排序的最终依据应该是实测**：用 `rv` 统计一趟 Linux 启动路径上"硬件乘法 / 软件乘法调用 / 常数除法 / 运行时除法"各占多少，再决定先加哪个。

### 3.5 `-march` 写法陷阱与验证方法

**陷阱：`m` 与 `zmmul` 不能同时用。** `Zmmul` 的定义就是"M 的乘法子集"（m = 乘 + 除，zmmul = 只有乘），所以：

```shell
# ❌ 冗余：m 已经包含乘法
-march=rv32ima_zmmul
# ✅ 正确：不含 m，只有乘法
-march=rv32i_zicsr_zifencei_a_zbb_zmmul
```

想要"有乘法、没除法"，**必须把 `m` 整个去掉**，而不是在 `m` 上加 `zmmul`。

**验证工具链是否支持：**

```shell
# 1. 列全部支持的扩展名（GCC 13+）
riscv64-unknown-elf-gcc -march=help | grep -E 'zbb|zmmul'

# 2. 直接试编译
riscv64-unknown-elf-gcc -march=rv32i_zicsr_zifencei_a_zbb_zmmul -mabi=ilp32 -c test.c

# 3. 确认它去哪找库（空 = 用默认库，可能拿错，见 no-rvc-toolchain.md）
riscv64-unknown-elf-gcc -print-multi-directory -march=rv32i_a_zbb_zmmul -mabi=ilp32
```

**看代码生成的直接证据：**

```shell
riscv64-unknown-elf-gcc -march=rv32i_zmmul_a -mabi=ilp32 -S test.c | grep -E 'mul|div'
# 期望：能看到 mul 指令（硬件乘法），看不到 div（除法变成 call __divsi3）
```

**参考实现：QEMU。** QEMU 的 RISC-V CPU 模型本身就是扩展位图，可逐位开关：

```shell
qemu-system-riscv32 -cpu rv32,zbb=true,zmmul=true ...
qemu-system-riscv32 -cpu help        # 列出支持的扩展名
```

这说明"细粒度组合扩展"是被预期支持的使用方式，不是钻空子。

**生态常见度参考：**

| 配置 | 常见程度 | 例子 |
|---|---|---|
| 极简核不带 M | 非常常见 | SERV（位串行，无 M）、PicoRV32（`ENABLE_MUL`/`ENABLE_DIV` 默认关）、VexRiscv（Mul/Div 为可选插件）、各类教学核 |
| 带 Zbb 的核 | 越来越常见 | 现代应用核普遍补 Zbb（成本低，编译器与库都能受益） |
| Zmmul（只有乘法） | 新、公开案例少 | 2021 年才批准，动机是"只要乘法"的面积敏感场景 |

### 3.6 待验证的问题

1. **无 M 的内核是否真能编出来**：改 march 后，除了 `__mulsi3` 一类符号，是否还有别处假设 M？
2. **OpenSBI / buildroot 是否也假设 M**：检查 `PLATFORM_RISCV_ISA` 与 buildroot 的 ISA 选项（参照 `no-rvc-toolchain.md` 第 2 节的方法）。
3. **面积数据**：乘法器（Booth + Wallace 树）与除法器（SRT 迭代）在目标工艺/频率下的资源占用对比——这是决定"要不要做除法器"的最终依据。
4. **性能量化**：若去掉硬件除法，在内核启动路径上的额外开销有多大（用 `rv` 或 QEMU 做指令数统计）。

## 四、与 `rv.c` 的呼应

同一个问题在软件与硬件两个层次出现：

| 实现 | 位置 | 层次 | 解决的问题 |
|---|---|---|---|
| `rvm()` / `rvm_ahh()` / `rvm_mhh()` | `rv.c` | **硬件** | 用 32 位运算实现 `mulh`/`mulhu`/`mulhsu` 的 64 位结果（手工进位链） |
| `div64_u64()` / `do_div()` | Linux 内核 | **软件** | 用 32 位指令合成 64 位除法 |

两者都在回答同一句话：**32 位机器上的 64 位算术，永远要有人来补。** 区别只是补在指令集里，还是补在库里。
