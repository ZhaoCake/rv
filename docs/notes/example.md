首先阅读example.c，非常简单的结构。

大体来说，就是初始化了mem和cpu，用rv_init来作初始化，需要传入机器和内存状态（的指针）以及总线的函数指针。接着把构造的program复制给rv的mem。

其中不理解的是bus的作用。

bus_cb是rv访问外部世界的唯一通道。rv有一个rv_bus_cb字段。rv的结构体全是寄存器状态，没有内存，所以取指令是走bus_cb的。我记得在nemu里面我们是直接改内存的，这个走bus_cb的方法，使得我们有了一个确定的事务产生？大概可以这样认为。

为了可以嵌到任何宿主，rv故意不在自己的“状态”里面分配内存。并且地址是碎片化的。
可以认识到，充分认识这个bus_cb的逻辑是理解能跑linux的rv要实现怎样的功能的关键一步。

在使用时写的这个bus_cb相当于提供了一个总线工作的逻辑，是功能级模拟里的"地址解码 + 转发"钩子。要理解它如何工作需要看到它在init时被指针指向后如何被调用，让我们定位到这段代码。

我们轻易知道，rv_bus相当于是读虚拟地址，bus_cb是读物理地址，有一个rv_vmm函数进行翻译，它会查页表（当然还是走bus_cb）。

首先为什么是不可达的。我还没完全理解。

因为12位页内偏移和4KB页大小，决定了最后一个字节只能是0xFFF，在对齐的情况下（那么对齐的检查在哪里呢？）。无法超过0x1000，不会出现跨页。
不，这只是对齐访问的情况。如果我要在0xFFE写一个四字节或者读一个四字节呢？由于RVC的存在，实际上rv_if里面确实有考虑处理这种事，但似乎直接拆成两个了，不用再在rv_bus里面考虑跨页处理的问题。
所以我可以这样考虑这个问题吗？跨页的问题会发生是因为引入RVC，但是处理器本身访存的支持，rv模拟器并没有去实现非对齐访存。非对齐取指的问题会出现是由于RVC导致的？

问了AI，AI给我纠正了一些，说是非对齐访存和非对齐取指

① 非对齐访存 —— 与 RVC 毫无关系。

```code
lw x1, 0(x2)      x2 里是什么值，编译器/程序说了算
```

x2 = 0x...FFE 时这条 lw 就是非对齐访问，无论有没有 C 扩展。RISC-V 规范对此的规定是：实现可以选择抛 misaligned 异常，也可以选择硬件支持。rv 选了前者：

```rv.c L433-L434
  if (*va & (width - 1))
    return RV_BAD_ALIGN;
```
这是合法实现，不是偷懒。真实处理器两种都有：很多嵌入式核抛异常，一些高性能核（或经过 M 模式软件模拟后）能处理。（Linux 5.19+ 有 arch/riscv/kernel/traps_misaligned.c 专门做软件模拟，正是为这类硬件准备的。）

② 非对齐取指 —— 这才真正源于 C 扩展。

没有 C 扩展时，所有指令都是 32 位，pc 必须 4 字节对齐。有了 C 扩展，16 位指令合法，pc 只需 2 字节对齐，于是可能出现 pc = 0x...FFE，此时：

取一条 32 位指令 → 地址不对齐（相对 4 字节边界）
同时跨页（0xFFE ~ 0x1001）

---

总之，如果是这样的话，我在实现我的处理器的时候，不考虑加入RVC。我是觉得RVC没啥必要，如果我的目的是跑起来Linux的话，不要RVC也行而且更容易一些，避免了非对齐访问的问题。
